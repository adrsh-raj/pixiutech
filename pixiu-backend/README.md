# PIXIU Tech Django Backend

Clean replacement backend for the PIXIU LMS.

## Stack

- Django
- Django REST Framework
- PostgreSQL via psycopg 3
- django-cors-headers
- SimpleJWT

## Rebuild rules

This backend starts against a fresh PostgreSQL database. Legacy Express/SQLite application data is not imported.

Business domains and authentication are added incrementally in the numbered rebuild steps.

No school, trainer, class, student, database name, password, or relationship is hard-coded in application logic.

## Phase 2 — Authentication, authorization and credentials

The backend uses a custom `accounts.User` model with JWT Bearer authentication. Access tokens are short-lived, refresh tokens rotate, and refresh tokens are blacklisted after use. Logout blacklists the submitted refresh token.

Four roles are defined: `admin`, `school`, `trainer`, and `student`.

Business actions are represented explicitly as `VIEW CREATE EDIT DELETE PUBLISH ASSIGN GRADE RATE EXPORT`.

Passwords are hashed with Django's password API. School credentials are admin-managed with a minimum of 8 characters; trainer credentials are admin-managed with a minimum of 12 characters. Student credentials are generated by the backend from the authoritative student identity and force a first-login password change.

Student ID format: `[SCHOOL_CODE][GRADE][SECTION] [ROLL_NO_2_DIGITS]`.

Example: `XYZ8A 03` → password `XYZxyz8A3@hata`.

## Phase 3 — Academic identity

`academics` contains relational `School`, `Trainer`, `TrainerSchoolAssignment`, `SchoolClass`, and `Student` records. School/trainer/student usernames are linked to those authoritative profiles. Duplicate trainer-school assignments, duplicate classes, and duplicate roll numbers are blocked at the database level.

## Phase 4 — Learning domain

The `learning` app now owns:

```text
Session
AttendanceRecord
CurriculumUnit + CurriculumClassAssignment
LearningContent + ContentClassAssignment
Quiz + QuizQuestion + QuizClassAssignment
QuizAttempt
StudentAssessment
Project + ProjectEvidence
```

Key rules:

- Sessions belong to a real class and assigned trainer.
- Attendance is unique per session/student and cannot be silently reassigned across classes.
- Curriculum, materials and quizzes are shared through explicit class-assignment tables rather than grade/string matching alone.
- Students see only their assigned class content.
- Quiz scoring happens server-side; correct answers and explanations are not exposed to student read APIs.
- Attempts are relational, numbered, and limited by the quiz's `max_attempts`.
- Reviews/assessments belong to a student and trainer.
- Projects and evidence belong to the authoritative student record.
- List querysets and object permissions enforce role scope.

## Local setup

```bash
cd pixiu-backend
python -m venv .venv
# Windows: .venv\\Scripts\\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env   # Windows
# cp .env.example .env  # macOS/Linux
python manage.py check
python manage.py check_database --strict
python manage.py migrate
python manage.py test
python manage.py runserver
```

## Environment rules

`DATABASE_URL` must point to the new PIXIU Django PostgreSQL database during this rebuild.

Set `DJANGO_EXPECTED_DATABASE_NAME` to the exact new database name. With that value present, the app refuses to start when the configured database name does not match it.

Set `DJANGO_ALLOWED_HOSTS`, `DJANGO_CORS_ALLOWED_ORIGINS`, and `DJANGO_CSRF_TRUSTED_ORIGINS` per deployment environment. Do not use a wildcard browser origin in production.

Never commit `.env`, real database credentials, Django secrets, or generated passwords.

## Deployment preflight

Before deploying a new environment:

```bash
python manage.py check --deploy
python manage.py check_database --strict
python manage.py migrate --plan
```

Only run migrations after `check_database --strict` confirms the intended fresh database. Do not point this backend at the legacy database.
